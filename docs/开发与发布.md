# 岚汐纪：潮晶之争 · 开发与发布

## 1. 交付定位

本工程交付第一阶段完整可玩的单人即时战略循环，并纳入部分第二阶段美术完善与第三阶段验证。它不是只有UI的演示：资源需要采集并运回，建筑需要施工，生产消耗资源并受人口限制，双方单位能寻路和交战，敌方AI真实发展，回响心被摧毁后进行胜负结算。

当前版本仍是可继续迭代的基础游戏工程，不等同于商业发行完成或所有平台验收通过。未包含联网、账号、支付、排行榜和多关战役。

## 2. 实际开发环境

| 项目 | 当前情况 |
|---|---|
| 引擎 | Godot 4.7.2 stable，标准 GDScript 版本 |
| 已发现引擎位置 | `godot` |
| 工程入口 | `project.godot`，主场景 `scenes/main.tscn` |
| 渲染 | GL Compatibility，正交3D镜头 |
| Houdini | 当前环境未安装，未执行许可证检查或实际资产生成 |
| 导出模板 | 当前环境缺少匹配的发布模板，需要后续安装 |

游戏运行不需要Houdini、Houdini Engine或联网服务。Houdini定位为离线内容制作工具，Godot负责游戏运行、输入、界面和发布。许可证与导出限制需要在实际安装Houdini后按所用版本核对。

## 3. 工程结构与职责

| 路径 | 作用 |
|---|---|
| `project.godot` | 项目、渲染、窗口、方向与入口配置 |
| `scenes/main.tscn` | 主场景入口 |
| `scripts/main.gd` | 应用流程、输入、镜头、选择、教学、存档和模块连接 |
| `scripts/game_data.gd` | 单位、建筑、资源、费用、名称和规则数值 |
| `scripts/simulation.gd` | 独立于渲染的经济、施工、生产、战斗、寻路、迷雾、AI与状态保存 |
| `scripts/world_view.gd` | 世界场景、地形、水面、实体显示、迷雾、视觉反馈及画质 |
| `scripts/asset_factory.gd` | 原创程序化模型与共享网格/材质构建 |
| `scripts/hud.gd` | 自适应HUD、教学卡片、菜单、说明书与设置 |
| `scripts/minimap.gd` | 海图绘制及镜头位置操作 |
| `scripts/selection_overlay.gd` | 框选覆盖层 |
| `scripts/soundscape.gd` | 程序合成氛围音乐与提示音，无外部采样音频 |
| `assets/fonts/` | 随附中文字体和字体许可 |
| `tests/sim_test.gd` | 规则与完整对局的headless检查 |
| `tools/play.command` | 本机macOS启动器 |
| `builds/` | 本机开发 App、PCK、日志、截图与测试输出；不应混作应用商店发布包 |

核心数据以实体字典保存，`pos: Vector2` 对应3D世界的 X/Z 平面，`team` 为0玩家、1AI、-1资源。世界为80×80。规则按0.1秒固定步长推进，渲染可独立使用更高帧率。UI应保持实体ID而不是跨读档持有旧实体字典。

新增单位时先修改数据定义，再补充模型、生产入口、说明和需要的规则；新增特殊能力不能只改显示文字。调整价格、人口或训练时间后，重新验证AI能发展、玩家能通关，并更新游玩说明书中的表格。

## 4. Houdini资产制作与接入

详见随附的 [Houdini工作流](ASSET_PIPELINE.md)。该文档及脚本负责资产参数、单位/坐标、命名、LOD、碰撞、导出与Godot接入说明。

当前画面来自Godot中的原创程序化几何组合，不是声称已经在Houdini中烘焙出的成品。后续Houdini资产应导出为常规GLB/glTF或目标引擎支持的中间文件，保留资产接口和一致尺寸，避免把商业制作许可证转变为玩家运行依赖。

替换资产时逐项核对：地面原点、X/Z占地、材质、正确正面方向、建筑施工状态、单位选择环、阵营视觉差异、动画节点和碰撞代理。程序化模型中的多部件结构与Godot材质，不能假定导入任意GLB后会自动形成同样的动画或交互接口。

目前未在Houdini内打开工程、执行生成、导出GLB或做视觉比对；这些操作是后续验证工作。

## 5. 输入与屏幕适配

电脑支持选中单位后普通点击目标下令、Shift追加、框选、右键上下文命令、方向键/中键/触控板手势移镜头、滚轮/捏合缩放和1至5编队。工人提供“采集”指令卡，所有单位有移动及沿途迎击指令卡，目标选择期间可点击取消。手机提供点选、连续多选、框选、单指移镜头、双指平移缩放，以及常用操作按钮。键鼠和触摸输入分别处理，触摸不会依赖右键或悬停。

项目设置 `display/window/size/mode=2` 使 Godot 的运行按钮使用独立最大化窗口；Godot 对最大化项目不启用固定尺寸嵌入预览。窗口还原及调整尺寸时，由运行时按照实际 viewport 同步布局及场景坐标。

HUD使用容器和动态布局，根据可用窗口大小切换紧凑状态；可滚动区域承载较多卡片和长说明。使用当前viewport进行地面投影，窗口变化时清空尚未完成的拖动/触摸状态，避免旧坐标继续触发命令。

读取系统安全区域以适配边缘遮挡；竖屏显示旋转提示并暂停战场。焦点丢失后清空指针、保存并暂停；回到应用后通过暂停菜单继续。菜单、说明、设置和竖屏层阻止战场输入。

真实刘海屏、屏幕旋转、手势导航、触控采样、多指取消、后台挂起/回收及高DPI仍须在目标设备上验证。窗口尺寸测试只能覆盖布局和坐标逻辑的一部分。

## 6. 存档格式与错误处理

`main.gd` 的外层战局文档包含格式名 `lanxiji-campaign`、版本、规则状态、镜头和教学信息。规则层 `save_dict()` 将Vector2变成数值数组，避免JSON丢失类型；`load_dict()` 先验证完整数据，再一次性提交，不在校验失败时部分改写现有比赛。

手动存档为 `user://campaign.json`，自动存档为 `user://autosave.json`。实际运行约每60秒和应用失去焦点时尝试自动保存，手动存档通过F5或菜单触发。使用临时文件写入后重命名，读取限制文件大小并验证格式。普通读取优先手动存档，没有手动存档时读取自动存档。选中列表和编队不保存。

修改存档结构时应提升版本，提供明确迁移或拒绝旧版本的说明，不应默认把缺失字段当作新机制已经完成。发布前需要验证目标文件系统的重命名、剩余空间不足、只读存储、移动系统强制终止和旧存档兼容行为。

## 7. 已执行的规则验证

运行：

```sh
godot \
  --headless --path '/path/to/lanxi-chronicles' \
  --log-file /private/tmp/lanxi-sim.log \
  --script tests/sim_test.gd
```

Godot 4.7.2 实际执行结果为 **69项通过、0失败**，本次约2.4秒。覆盖：

- 采集、负重、回营入账、切换资源、正确扣费和不足反馈。
- 占地/越界检查、工人施工、完工人口、生产队列、人口预占和重复研发。
- AStar绕障到达、探索新增、离开后保留探索、停止和非法命令。
- 兵种克制、真实伤害、单位死亡、哨塔攻击、基地摧毁后的胜负及结束冻结。
- JSON存档往返、恢复生产与采集、非法坐标/重复ID/负资源/未知队列/缺失数据的原子拒绝。
- 同初态同指令一致结果、AI经济/建造/生产/行军/袭扰和持续模拟。
- 从正常初始资源出发，通过真实采集、施工、生产和攻击前进击败AI的完整对局。

完整对局用例约153秒胜利，没有直接生成玩家军队、赠送资源或修改敌方生命。AI自然进攻的无人操作测试约231秒触发玩家失败。前者验证存在可完成的流程，不等同于面向所有水平玩家的平衡性结论。

原生窗口与界面验证由主程序的 `--visual-test` 开发入口执行，截图和日志输出到 `builds/`。已读取的 `builds/visual-test.log` 显示，在本机Apple M5、OpenGL Compatibility渲染器下，采集指令、建造指令、建筑完工、资源交付、单位生产及存读档检查均为 `true`，各截图保存状态为0。

该次原生窗口检查包含1280×800、1024×768、844×390、390×844和1440×620；竖屏390×844正确报告 `portrait=true`、`blocks=true`。截图已做视觉检查。测试结束时的帧率快照不作为性能结论；另有开局与合成压力场景的短时采样，详见验收记录。手机尺寸窗口也不代表手机或 Windows 安装包已经验收。

## 8. 性能目标与后续验收

当前默认最高60FPS，提供流畅、均衡、精致三档，调整阴影和场景装饰。规则层与画面分离，并采用共享几何和实例化装饰。未给出所有设备固定帧率承诺。

后续基准测试应记录设备型号、CPU/GPU、系统、分辨率、画质、单位总数、建筑数、测试时长、平均及低分位帧率、内存和功耗。优先以目标电脑稳定60FPS、目标手机稳定30FPS作为优化方向，通过真实设备数据决定默认档位。

需要完成的验收包括：

1. 原生Windows/macOS构建，从启动到胜负、存读档、暂停恢复与多次重开。
2. Android/iOS真实触控、刘海/圆角安全区、横竖切换、后台恢复和系统中断。
3. 最低配置下的长时间经济/战斗、约定最大单位规模及明显卡死/内存增长排查。
4. 连续缩放、超宽屏、高DPI、文本滚动、菜单输入阻隔及快捷键焦点。
5. 安装升级与旧存档、权限、磁盘不足及崩溃恢复。

## 9. 各平台发布路径

先在Godot中安装与 **4.7.2** 完全匹配的导出模板，再创建平台导出预设。模板当前缺失，工程中存在源文件不等于已经生成可安装包。

### macOS

可继续使用本机Godot运行工程。要分发独立应用，需要导出macOS应用并在目标macOS机器测试。公开分发时按分发渠道准备签名、公证、图标和隐私说明；当前本机启动器不等同于经过签名公证的正式App。

### Windows

创建Windows Desktop预设，检查渲染兼容性、中文字体、窗口模式、存档目录及高DPI。导出后在真实Windows设备上跑完整验收，不能以macOS下的headless测试代替。

### Android

准备目标Godot版本要求的Java与Android SDK，设置包名、版本、图标、屏幕方向及签名。先导出开发包安装到真实Android设备，验证多指、系统返回/后台、权限及性能，再准备发行密钥和商店材料。不要把签名私钥写入仓库。

### iOS

准备受支持的Xcode、iOS SDK、Apple开发与签名环境。导出Xcode工程后，在真实iPhone/iPad检查方向、安全区域、音频中断、触摸和后台行为。构建成功、开发签名可安装和App Store审核通过是不同阶段，当前均未宣称完成。

## 本机开发包与最终验收记录

当前已生成 `builds/岚汐纪.app`（Apple Silicon），包含引擎运行时，可以独立启动。构建脚本是 `tools/build_macos.command`，使用本机已有的 Godot 可执行文件并做本地临时签名。它比正式模板导出包更大，且未公证。Windows、Android 和 iOS 发布仍需对应工具链。

## 输入与血条回归

运行 `python3 tests/check_runtime.py` 会创建临时项目和独立用户数据目录，在原生 Godot 窗口执行输入、血条投影及集成检查，再运行 HUD 尺寸回归。结果复制到 `builds/laptop-health/`，不会改写玩家的存档。`tests/health_bars.gd` 覆盖生命比例、镜头角度、缩放、移动、施工高度、迷雾、死亡和重置。血条使用统一的朝向镜头父节点，按模型包围盒定位，前景与背景共享坐标，避免扣血时横向偏移沿世界坐标计算。

新增职业由 `game_data.gd` 中的 UNITS、COSTS、ROLES 定义，骑士和枪卫沿用现有寻路、生产、人口与存档架构。回响心和织锋庭使用独立真实训练队列。`simulation.gd` 的 `difficulty` 随存档保存；缺失该字段的旧档迁移到休闲。`tests/content_rules.gd` 验证招募费用、兵种克制与休闲波次；`tests/content_ui.gd` 验证中央招募、警报、模型关节与动作。


## UI 视觉系统与回归

`ui_theme.gd` 集中管理配色、字号、触控尺寸和控件状态；`ui_icons.gd` 缓存原创 SVG 与离线模型缩略图。HUD 保留既有 action 和 map_clicked 信号，字号偏好保存到 settings.cfg 的 display/large_text；旧配置缺省为正常字号，战局存档不变。

新增 `tests/ui_refinement.gd`（原生渲染、截图与布局/招募/触控专项）及 `tests/ui_interaction.gd`（实际输入与内容回归）。`tests/window_layout.gd` 同时验证正常和 125% 大字模式，不再要求所有文字固定至少 22。运行截图测试时仅使用 builds 下的测试存档，设置不会写入用户偏好。

缩略图重建顺序：用非 headless Godot 运行 tools/render_ui_portraits.gd，然后执行 headless editor import；所有缩略图均为静态纹理，不新增游戏中持续渲染的 3D 预览。可选前后对照：ui_refinement.gd 接受 --baseline-hud=/absolute/path/to/old/hud.gd，同一冻结战场分别渲染两个 HUD；随后运行 tools/make_ui_comparisons.py 合成 PNG。
